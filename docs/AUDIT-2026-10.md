# 工业级体检：清单、发现与修复（2026-10-29）

这份文档回答一个问题：**「这个软件凭什么不会把图纸弄丢？」**
它把外部成熟做法（GitHub 上的资料）变成逐条可执行的检查项，再对着本项目的代码
一条条核，查出问题就修、修完补测试。

> 说明：本次 `WebSearch` / `WebFetch` 在本机被网络策略挡住（403 / 域名安全校验失败），
> 所以资料是用 `curl` 直接拉 GitHub 原始文件读的，来源列在下面。

## 一、依据（GitHub 原始资料）

| 来源 | 拉到的内容 | 用在本项目的哪一条 |
|---|---|---|
| `git/git` → `Documentation/git-fsck.adoc` | 完整性校验的完整模型：`missing` / `hash mismatch` / `dangling` / 引用一致性，以及「坏对象只能从别处备份找回」 | 体检（`fsck`）与从对端修复（`repair`） |
| `dastergon/awesome-sre` | 生产就绪评审、混沌工程（Principles of Chaos）、事后复盘（blameless postmortem） | 「随机强杀进程」的崩溃一致性实验；发现必须闭环 |
| `jbd.dev/prod-readiness`（SRE 清单） | 可复现构建、消除单点、明确外部依赖可用性、备份与恢复演练 | 双机互为备份、备份保留策略、恢复演练 |
| `danluu/debugging-stories` | 真实事故类别：只在特定机器坏（sparc64 数据损坏）、只在特定时间崩、部分失败、同步相关崩溃 | 环境相关（磁盘/路径/编码）、时序、部分写、静默损坏 |

归纳出的**十条铁律**（本项目版）：

1. 内容必须能自证：每个对象用 sha256 命名，读的时候重算一遍，不信任长度。
2. 任何写盘要么完成要么没发生：临时文件 + 原子替换，不许原地改。
3. 写之前先体检：能不能写、盘够不够，不行就一个字节都别动。
4. 写到一半必须能退回去：备份 + 回滚；连「断电被强杀」也要留痕、能收尾。
5. 坏了要能修：缺的/坏的对象能从另一台机器按对象号补回来。
6. 备份要有上限：无限增长会把盘塞满，塞满了连一次记录都做不成。
7. 陌生人乱打不能把服务打挂：4xx，绝不 5xx，绝不掐断连接。
8. 部分失败要显式：读不了的文件不许悄悄从版本里消失。
9. 恢复必须幂等：同一个版本恢复多少次，结果都一样。
10. 结论要能被别人重跑：每条都落成自动测试，能反复跑。

## 三、本轮发现并修掉的问题

### 1. 未知接口/鉴权失败时，服务端先关连接 → 客户端看到「连接被重置」

- **现象**：模糊测试 500 次里偶发 1 次 `ConnectionResetError(10054)`，界面上就是「请求失败」，
  但实际上什么都没坏。
- **根因**：`do_POST` 的早退分支（404 未知接口、401 令牌、415 类型不对）从不读请求体。
  客户端还在发 body，服务端已经回包关 socket，Windows 直接发 RST，把还没读走的响应一起丢掉。
- **修法**：`_send()` 回包前统一 `_drain_body()`，按 `Content-Length` 把没读的字节吃掉（上限 8 MB）。
  一条机制覆盖所有早退分支，将来新加路由也不会漏。
- **弊端**：拒绝一个 8 MB 以内的超大上传时会多花一点时间读掉它。
- **对策**：超过 8 MB 不陪着读，直接关连接；正常请求体（KB 级）代价可忽略。

### 2. 坏 JSON 让服务端「等第二批字节」，直到客户端超时

- **现象**：接口模糊测试整体从 20 秒退化成 5 分钟以上。
- **根因**：`body_json()` 先读后解析，解析失败时没记账，回包前又去 drain 同一批字节，
  而客户端不会再发第二遍 → 线程卡住，客户端 20 秒超时。
- **修法**：先记账再解析（读进来多少就扣多少）。
- **弊端**：无。
- **对策**：加测试 `test_bad_json_leaves_no_unread_bytes`，要求 5 秒内回 400。

### 3. 对象读出来不校验哈希 → 坏数据会被当成图纸写回去

- **现象**：磁盘静默损坏、被别的程序改过、老版本写到一半留下的对象，长度是对的，内容不对，
  恢复时照样写进工作区。
- **根因**：`get()` / `blob_to_file()` 只校验头部长度。
- **修法**：`get()` 读完整对象后重算 sha256 与对象号比对；`blob_to_file()` 边流式写边算，
  写完不匹配就丢弃临时文件、目标文件一个字节不动。
- **弊端**：每次恢复多一次哈希计算（约 500 MB/s，1.9 GB 的图纸多几秒）。
- **对策**：只在「恢复/导出/预览读对象」时算，扫描比较不改路；用 `.zgr-part` 保证失败不留残迹。

### 4. 坏对象解压抛 `zlib.error`：绕过回滚，接口直接 500

- **现象**：恢复过程中遇到坏对象，异常类型不是 `RepoError`，`restore()` 的 `except (RepoError, OSError)`
  接不住 → 不回滚、不清理，接口层再包成 500。
- **修法**：`_iter_raw()` 把 `OSError/zlib.error` 统一翻译成 `RepoError`；顺带给 `blob_to_file` 加
  `try/finally` 清理临时文件。
- **弊端**：无。**对策**：`test_failed_restore_clears_journal_after_rollback` 覆盖。

### 5. 没有「体检」，也没有「修复」

- **修法**：新增 `Repo.fsck(deep=False)`（连通性，快）与 `deep=True`（逐对象重算校验和），
  返回 `missing / bad / dangling / errors`；新增 `zgr fsck`、`GET /api/fsck`、界面「🩺 体检」按钮。
  新增 `sync.repair()`：把对端当备份，按对象号补齐缺的、删掉坏的再重下，只动物件库。
- **弊端**：深查要读一遍全部对象（大项目几分钟）；repair 依赖对端有同一份历史。
- **对策**：默认浅查、需要时深查；repair 结束再做一次体检，补不全就如实说「远端也不全」。

### 6. 恢复被断电/强杀后，工作区半新半旧且无痕迹

- **修法**：恢复开始前写 `.zgr/restore-journal.json`，成功后清除；下次打开项目时
  `/api/project` 带出 `pending_restore`，界面顶部横幅给出两个按钮：
  「继续做完」（重跑恢复，幂等）和「回到恢复前」（把备份原样拷回）。
- **弊端**：多一个小文件；同一时刻只能记一次恢复（本来就串行）。
- **对策**：回滚成功或正常完成都会清掉日志；`zgr recover` 命令行同样可用。

### 7. 备份只增不减，迟早把盘塞满

- **现象**：实测两台机器分别堆到 25 批 / 38 批，合计 1.8 GB。
- **修法**：`Repo.prune_backups(keep=20)`，只认自己命名的批次目录，先算大小再删，删不掉不谎报；
  `zgr backup --prune [--keep N] [--dry]`、`POST /api/backup/prune`。
- **弊端**：超过保留数的旧备份会被删（这是设计意图）。
- **对策**：默认留 20 批，`--dry` 可先演练；不是本软件命名的目录一律不碰。

### 8b. 带 BOM 的 JSON 被当成「文件不存在」

- **现象**：真机冒烟时手工写了一个带 BOM 的恢复记号，接口返回「没有中断的恢复」。
- **根因**：`_read_json()` 用 `utf-8` 打开；BOM 让 `json.load` 抛 `ValueError`，被吞成 `default=None`。
  记事本（老版本）改配置就带 BOM，用户会以为自己设的项没生效。
- **修法**：改用 `utf-8-sig`；同时让「记号文件存在但读不出来」报 `corrupt=True`，
  界面和命令行都明确提示，而不是假装什么都没发生。
- **弊端**：无。**对策**：`test_journal_with_bom_is_still_read`、
  `test_corrupt_journal_is_reported_not_ignored`。

### 8c. 写盘半成品可能被当成项目文件记录进版本

- **修法**：临时文件统一后缀 `.zgr-part`，`ignored()` 里硬编码排除（不受用户忽略规则影响）。
- **弊端**：无。**对策**：崩溃测试断言工作区里没有半截文件。

## 四、仍然存在的边界（如实列出）

1. **跨进程同时操作**：已加按项目的文件锁（`.zgr/lock`），网页服务和命令行会排队。
   边界在于：一个超长恢复（几分钟）期间，另一个进程的记录动作会等到超时后报「另一个程序正在操作」，
   而不是插队硬写——这是有意选择的「宁可等一下，也不冒险」。
2. **大小写重名**：两台都是 Windows，`Part.sldprt` 与 `part.sldprt` 不会共存；
   若将来接 macOS 对端，恢复时后写的会覆盖先写的。需要时在同步入口做冲突检测。
3. **超长路径**：本机（Windows 11 + 长路径已启用）实测 322 字符可提交、可恢复；
   远端机需要在部署后复核一次。
4. **磁盘物理损坏**：连续坏块可能同时伤到对象库和备份，唯一兜底是另一台机器的副本，
   所以「双机同步 + 定期体检」是必须的日常动作，而不是可选项。

## 五、日常怎么用

```bat
:: 查（只读，随时可跑）
zgr fsck  D:\项目\示例图纸
zgr fsck  D:\项目\示例图纸 --deep

:: 修（把另一台机器当备份）
zgr repair D:\项目\示例图纸 --url http://192.168.1.10:8795

:: 备份太多时
zgr backup D:\项目\示例图纸 --prune --keep 20

:: 上次恢复到一半断电了
zgr recover D:\项目\示例图纸
```

界面上：左侧「🩺 体检」；恢复被中断时顶部会出现黄色横幅。
